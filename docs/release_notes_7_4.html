DataReel 7.4 beta 3 (tag 7.4-beta3, 11/14/2026) follows beta 2 with the replication fixes and the security scan below (BETA 3). Beta 2:

DataReel 7.4 beta 2 (tag 7.4-beta2, 11/14/2026): the OODB with AI extensions. It follows the 11/12/2026 7.4-beta preview (tag 7.4-beta, 171a3f2: vector phases A and B) and adds vector phases C and D (below), the gxrepl fixes F4, F6 and F7, the DataReel 7.3.2 replication fixes and the later ones of rel-7.3.2-next3 (the seal per folder, a stream naming new files verified again, promote-check reading each unit under a shared apply lock, GXREPL_TORN_LOCK_WAIT 15 s), and the gxrepl per-object derived apply (derived_apply = incremental, with object notes and index stamps; off by default: rebuild stays the default and the ship log is unchanged while object notes are off; see utils/gxrepl/DERIVED_APPLY_STATUS.md). derived_apply = incremental is not yet for production use; fixes land in the next 7.4 build. The file formats of 7.3 are unchanged, and the vector index is a new file type built on them.

New in 7.4.1 (11/20/2026)

  • gxObjRepl uses port 2073 by default: replication is a gxStream object stream, and 2073 is the gxStream port registered with IANA (gxs-data-port). A copy with no "listen" port listens on 2073, and a primary whose "copy" setting has no port connects to 2073 (gxObjReplConfig::listen_port is 2073, copy is HOST[:PORT]). "listen ADDR" sets only the address. Configs that name a port work as before; a bad copy or listen value is refused at start. utils/objrepl/test_objrepl_config.sh checks both (it needs 127.0.0.1:2073 free).
  • Security fix, the object service (gxdbobject.cpp): an address a client sends must be the start of a normal (not deleted) block inside the file, and for a writable database one of its live objects (the server keeps the list, made when the database opens). 7.4 checked only the check word of the block header in front of the address, so a client allowed to write could copy a block header into its own object and CHANGE or DELETE at the address behind it, writing past that object into the next ones; REQUEST could read past an object or read deleted blocks. Only clients that passed mutual TLS and the allow list could do it. tests/object_service_test.cpp (19 checks, 10 of them fail on 7.4) runs in run_tests.sh.
  • gxObjRepl fixes (11/19/2026), seen with a copy on a slow disk: utils/objrepl/test_objrepl_stall.sh (a test build: -DGXREPL_TEST_HOOKS=ON) fails on 7.4 and passes on 7.4.1.
    • The primary's Pump() could wait in a socket read for 10+ minutes. One exchange (a frame and the copy's answer) now has a total deadline, the new ack-timeout setting (default 300 s; objrepl --ack-timeout S). Past it the connection is shut down and dropped and Pump() returns. The connect and handshake take at most 30 s, or ack-timeout when that is less.
    • The copy served one connection at a time and did not watch its listener, so the primary's new connections waited unaccepted (CLOSE-WAIT, the TLS hello unread) until the old connection went idle for idle-timeout seconds. The copy now takes a new connection that passes the TLS client check at once and drops the old one; one that fails the check is closed.
  • New: gxObjReplReader (gxobjrepl.h), read-only access to a node's databases from other processes while the node runs (gxObjRepl holds a node folder for one process). Get, IsLive, Ids, Databases, FindKey and Nearest, each under the node journal's shared lock, so a call sees whole commits only; Seq() names the commit read. A call opens and closes the files it needs; a loaded vector index stays in memory and is read again when the node moves on. The 64-bit engine only. utils/objrepl/test_objrepl_reader.sh.
  • gxdJournal: SetWriteLock(1) now covers write-back mode as well (WriteCommitted() and checkpoints), and Recover() holds the lock while it replays, so a gxdJournalReadLock reader never sees a batch half written. gxObjRepl nodes turn the write lock on.
  • KNOWN_ISSUES.md: the known limits, untested areas and flaky tests.
  • Documentation: docs/security_white_paper.md, the security design of the library; docs/gxstream_replication_white_paper.md, gxStream and replication on port 2073; docs/rfc/draft-gaer-datareel-gxstream-00, the protocol's specification (an Internet-Draft for the Independent Submission stream, which also covers the DataReel 6.x legacy transports).

Highlights of 7.4

  • Object replication between Windows and Linux (gxObjRepl, gxobjrepl.h, beta 5): Windows and Linux nodes replicate objects in both directions, with the primary on either side, and takeover and rejoin work across the two platforms. See NEW IN BETA 5.
  • The vector index (gxvindex.h): exact and graph search, float32, float16 and int8 vectors, vector members of records, day sets and vector searches through the database object server (phases A to D).
  • One database file layout on every platform (beta 5): files and record addresses move between Windows, Linux, 32-bit and 64-bit builds, and files of the old 4-byte layout keep working.
  • Network classes and examples: an IMAP client (gxsIMAPClient), https_check, and UDP broadcast and multicast.
  • Removed in beta 5: gxrepl page-shipping replication (see NEW IN BETA 5).

Phase a (11/12/2026): vector index file, exact search

New headers gxvindex.h (gxVectorIndex, gxvFilter, gxvResult) and gxvkern.h (distance kernels); sources src/gxvindex.cpp and src/gxvkern.cpp; test program utils/vix_test.

1. gxVectorIndex keeps vectors in a ".vix" file, which is an ordinary

   gxDatabase file: a 256-byte static area (magic "GXVIX74", version,
   dimension, element type, metric, M / M0, ef_construction, node
   size, entry node, counts and a 63-character spec) and one
   fixed-size block per node (64-bit object id, flags, level, four
   32-bit tags, upper-level block, neighbor slots, vector). The graph
   of phase B uses the neighbor slots already reserved in every node,
   so phase A files open unchanged later.

2. Insert / Update / Delete (a tombstone) / Get / Contains, each a few

   writes to the file. Attach the index to a gxdJournal with
   j.Attach(vix.Database()) and a commit carries an object, its B-tree
   keys and its vector together; Rollback() then Reload().

3. Exact(query, k, results, filter): the k nearest live nodes, sorted

   by distance then id. gxvFilter tests tag ranges (equality is a
   range of one, so session, kind and a date upper bound are all
   tags) and an optional accept callback. (Search() was Exact() until
   phase B.)

4. Metrics: squared L2, cosine (vectors stored unit length, distance

   1 - cosine) and inner product (minus the dot product). Float32
   only in phase A; float16 and int8 come in phase C. Dimension 1 to
   4096. NaN and infinite values are refused.

5. Spec guard: Create(..., spec) stores a text such as

   "anomaly/shock/v1/<builder hash>"; Open(name, mode, spec) refuses a
   file with another spec, so vectors from a different feature
   builder never mix in one index.

6. Concurrency: the ids, tags and vectors stay in memory while the

   index is open, so searches never read the file. Searches share a
   lock; writers take it exclusively and go ahead of new searches
   (writer preference), so steady searching never stalls inserts.

7. Kernels: 8 partial sums in a fixed order, the same on the SSE2

   path and the plain C path (bit-identical results); plain C-style
   functions so the 6.x version shares them word for word.

8. Verify(resolve, data, bad, report) compares the file with memory

   and asks the caller whether each node's object still exists.

Tests (vix_test, 32-bit and 64-bit database engines): kernels against the written-out order; Exact against a brute-force reference for all three metrics with tag, range and callback filters and equal-distance order; create / insert / update / delete / reinsert / reopen / read only / spec mismatch / bad files; journal commit and rollback; three reader threads searching during 20,000 inserts and deletes (clean under ThreadSanitizer); 45 kill -9 rounds during committed batches: every round recovered exactly the committed batches, never a partial one.

Measured (4-core VM, dimension 79, k = 20): insert about 5 us; exact search of 30,000 vectors 0.9 ms p50, 150,000 6.7 ms, 1,000,000 55 ms (memory bound); opening 1,000,000 nodes 2.3 s. Sub-millisecond search over large sets is phase B's graph.

Phase b (11/12/2026): hnsw graph search, merge, repair

1. Search(query, k, results, ef, filter) walks an HNSW graph kept in

   the neighbor slots of each node plus an upper-level block for the
   nodes above level 0. A node's level is an integer hash of its id,
   so the same inserts in the same order build the same graph on every
   node. Up to 4096 nodes, and for filters (or tombstones) that leave
   fewer than about 5% of the nodes, Search() is Exact().

2. Filtered graph search: every node is a stepping stone, only live

   nodes that pass the filter are results.

3. Live inserts: Insert() works out its links under the shared lock

   (searches keep running), writes the file, then takes the exclusive
   lock only to link the node (microseconds). Per-node arrays grow in
   fixed chunks, so growing never copies what is there.

4. Update() with the same vector rewrites the tags in place; with a new

   vector it deletes the node and inserts a new one in one step.
   Deleted nodes stay in the graph until Repair().

5. Repair() rebuilds the graph from the live nodes and writes it.

   Merge(out, inputs, spec) builds one index from many files (the day
   files of a month): same dimension, metric and spec, ids unique
   across them, tombstones left out, every link written once.

6. Phase A files open unchanged: the graph is built in memory at Open()

   (GraphSaved() = 0) and Repair() saves it. A damaged link in a saved
   graph is handled the same way. Verify() also checks every link
   against the file.

7. Fix: the 256-byte header was written at FAU 256 (gxDatabase

   StaticArea() returns the static area's size, not its address), so
   the first node block overlapped header bytes 96-255. It now sits at
   FileHeaderSize(). Phase A was never installed, so no file has the
   old layout.

Tests (vix_test, 32-bit and 64-bit database engines, 11,897 checks): recall against Exact for all three metrics (20,000 clustered vectors: 1.000 / 1.000 / 0.996 at ef 64), filtered recall, a selective filter equal to Exact, the graph read back from the file gives the same answers, the same inserts build the same graph, deletes (no deleted node returned) and updates, Repair(), a phase A file and a damaged link rebuilt and repaired, Merge() of three day files (and its refusals), 45 kill -9 rounds on each engine (all recovered exactly, Verify() clean including every link), three searchers during 20,000 inserts and deletes, clean under ThreadSanitizer.

Gate (vix_test --gate 1000000, 4-core VM, dimension 96, M 16, ef_construction 200, k 20; one thread inserting in journal batches of 100 while three threads search):

  • Clustered vectors (1000 centers, like real features): build 526 s (0.5 ms an insert); quiet ef 64 recall 0.987, p50 0.17 ms, p99 0.34 ms; live: 1,053 inserts a second during 425,758 searches, p50 0.18 ms, p99 0.61 ms (p99.9 1.4 ms); recall after 0.986; ef 128 recall 0.999 at p99 0.53 ms. Gate met.
  • Uniform random vectors (pure noise, the worst case for any graph index): p99 0.84 ms live but recall only 0.23 at ef 64; at 50,000 nodes ef 64 / 256 / 1024 give 0.58 / 0.88 / 0.99. Noise has no near neighbors to find; real feature vectors are not like this, but a feature builder whose vectors look like noise needs a larger ef or Exact().
  • Opening the 1,000,000-node file (nodes and graph): 8.6 s.

Build fix (11/12/2026, found on RHEL 10): GCC fuses a*b + c into one multiply-add (FMA) instruction on x86-64-v3, RHEL 10's baseline, which changed the last bit of some distances and failed vix_test's bit-exact kernel check. gxvkern.cpp and vix_test.cpp now turn contraction off with a pragma, and the CMake files also build them with -ffp-contract=off. The crash test now waits until the child has created and synced the file before it starts the kill timer, so a slow machine no longer kills the child before its first commit.

Phase c (11/12/2026): float16 and int8 vectors, vector members

1. Element types gxvFLOAT16 and gxvINT8 (types 2 and 3 in the header).

   A node stores its vector as a code: float32 4 * dim bytes; float16
   2 * dim bytes (IEEE binary16, round to nearest even, subnormals
   kept); int8 dim signed bytes and a float32 scale per vector
   (s = max|v| / 127, q = clamp(lrintf(v / s), -127, 127), each value
   within s / 2). Node size = 48 + 8 * M0 + the code bytes; the header
   check follows the type. gxvFLOAT32 files are byte-identical to
   before (no version change); a library that does not know a type
   refuses it with gxv_UNSUPPORTED.

2. gxvCOSINE vectors are normalized, then stored. Every distance, in

   inserts as well as searches, uses the decoded vector, so Insert(),
   Repair() and Merge() build the same graph (vix_test checks it for
   every type and metric). Queries are not rounded. Get() returns the
   decoded vector; Update() compares stored codes.

3. float16 values above 65504 in size are refused with the new error

   gxv_OUT_OF_RANGE (added at the end of gxvError).

4. gxvkern.h: gxv_f16_from_float(), gxv_float_from_f16(),

   gxv_i8_encode(), gxv_i8_decode() (plain C, for the 6.x version).

5. Vector members: a record carries its vector in the index's stored

   form. MakeMember() returns MemberSize() bytes: a 12-byte head
   ("GXVM", element type, dimension, CRC-32 of the spec) and the code.
   Store it as an InfoHog member or a fixed char field of a POD
   record. InsertMember() / UpdateMember() put the code in the index
   unchanged, so record and node hold the same bytes, and refuse a
   member of another type or dimension (gxv_BAD_ARG) or spec
   (gxv_SPEC_MISMATCH). MemberVector() decodes one; MemberMatches()
   compares a record's member with its node (for a Verify() resolver).
   Rename(old_id, new_id) follows a record that moved: an InfoHog
   record that grows gets a new address. Write the record and the index
   in one gxdJournal transaction (attach the data file, its index files
   and the .vix): a crash leaves both or neither.

Tests (vix_test): search, graph, reopen, rebuild, delete, Repair, Merge and crash tests for all three types; all 63,488 finite float16 values converted both ways, rounding ties, subnormals and the 65504 limit; the int8 error bound; InfoHog records with a vector member and their index under one journal (changes, moves, rollback, 10 kill -9 rounds per type) and a POD record with a vector field. 53,469 checks. Recall at ef 200 against the exact answer on the float32 vectors (20,000 clustered points, dimension 32): float16 0.994 to 1.000; int8 0.980 (L2), 0.985 (inner product) and 0.947 (cosine: unit vectors in tight clusters, where neighbors differ by less than a quantization step).

Gate (vix_test --gate 1000000 --dim 96 --type ..., the same set and machine as phase B; the build times are rough, other jobs shared the machine):

  type   build   file    memory  quiet ef 64          vs float32  live (1 writer, 3 searchers)
                                 recall  p50   p99    exact ef 64 inserts/s  p50    p99
  f32    923 s   697 MB  779 MB  0.987  0.16  0.34    -           990        0.19   0.50
  f16    1308 s  515 MB  592 MB  0.987  0.35  0.67    0.986       488        0.42   1.11

Memory and file size include the graph (M0 = 32 links per node), which is now the larger part: the vectors take 384 / 192 / 100 bytes a node. float16 searches take about twice as long because each value is converted with a function call; a faster float16 decode (proved to give the same bits) is a possible later step. int8 is as fast as float32 and the smallest; use float32 or float16 where recall must stay above 0.98.

Phase d (11/14/2026): speed, growth, sets, vector search service, vectors under gxrepl

1. float16 speed: a 65,536-entry table decodes a half (proved against

   the scalar conversion for every one of the 65,536 bit patterns), and
   gxv_l2sq_f16() / gxv_dot_f16() decode 8 values at a time into the
   same 8-lane sums as the float32 kernels, so the distances are the
   same bits as decode-then-kernel (checked for dimensions 1 to 96 and
   4096). At 200,000 x 96 a float16 search now takes about as long as a
   float32 one (p50 0.146 ms against 0.137 ms; before: about twice as
   long). Files and results are unchanged.

2. int8 cosine: the decoded vector is normalized again, so cosine

   distances use unit vectors. Known limit, stated plainly: at
   1,000,000 x 96 the int8 cosine recall against float32 exact is
   0.9505 at ef 64 (0.972 at ef 200), just over the 0.95 bar. For
   cosine at that scale use float16 (0.986) or search with ef 128 or
   more.

3. Format fields for growth (static area offsets 140-255, zero in the

   files of phases A-C, which open unchanged and search the same: the
   test opens files made by the phase C library, 32-bit and 64-bit):
   features_required (a bit this library does not know makes the file
   gxv_UNSUPPORTED), features_optional (bit 0 tag ranges kept, bit 1
   derived from record members), codec (0; 1 is kept for product
   quantization), graph layout (0), partition id and count, tag_min[4]
   and tag_max[4] (the range of each tag over every node inserted:
   written with the counts in the caller's transaction, never narrowed
   by Delete(), worked out again by Repair() and Merge(); an empty index
   holds 0xFFFFFFFF..0), and 56 reserved bytes (written as zero, ignored
   when read). TagRange(), TagRangeExcludes(), SetPartition(),
   SetFromMembers(). New error gxv_INDEX_FULL at 4,294,967,280 nodes.

4. gxVectorSet (gxvset.h): many .vix files searched as one: day files,

   partitions, or both, listed in a plain-text manifest
   "<name>.vixset" (set, version, spec, dim, element, metric, codec,
   and per file its relative path, node counts, the range of tag 2 (the
   day, yyyymmdd) and a CRC-32 of the header fields that never change).
   Unknown lines are errors, paths are relative with no "..", writes go
   to a temporary file and are renamed. Files open lazily (read-only, an
   LRU of max_open), a search with a day range skips the files outside
   it unopened, searches run on several threads, and the results are
   sorted by distance, then file, then id: the same for any number of
   threads, and the order of a per-day merge that keeps the earlier day
   on a tie. The live day: a file that changed since it was read is read
   again (a file replaced by a rename is opened again), or a writer puts
   its own open index in the set with AttachOpen(). A listed file that
   is missing (an archived day) is skipped and counted, unless strict.
   gxVectorSet::OpenFile() treats one .vix as a set of one.

5. The object server answers vector searches (gxdbobject.h): a [db NAME]

   with "vectors = <.vixset or .vix>" takes op 7 VECTOR_SEARCH (k up to
   1000, ef up to 4096, a tag filter, a day range, strict) and op 8
   VECTOR_INFO on its channels, read-only. The reply starts with the
   request version, and names the result files by their paths relative
   to the manifest. vector_threads (2) and vector_max_concurrent (4: one
   more waits up to 5 s, then is answered "busy"). Vectors inside a set
   the server copies are searched under the set's apply lock.
   object_client --vinfo and --vsearch K show the use.

6. Vectors under gxrepl: a vector index can be derived from the vector

   members of its data file's records (gxvmember.h), so a replicated
   copy never needs the .vix bytes. The set names it "derived"; the
   writer leaves it out of its ship log (gxdShipLog::SetExclude), the
   file sync never sends it, and the copy rebuilds it with
   utils/vix_rebuild as its derived_rebuild:

     derived = vectors.vix
     derived_rebuild = vix_rebuild --data {dir}/data.gxd
         --index {dir}/vectors.vix --member infohog:1 --tags -,-,infohog:2,-
         --dim 96 --spec news/v1 --stamp-dir {dir} --lsn {lsn}

   The node id is the record's address; a record without a valid
   member is not in the index; the rebuild goes in ascending address
   order, so two rebuilds of the same data are the same file byte for
   byte, and it marks the file derived from members. While the copy's
   index is behind, "gxrepl torn" warns (INDEXES), never TORN.
   vix_rebuild --digest prints a logical digest (the live nodes in id
   order: id, stored code, tags; equal for a primary's index built in
   commit order and a copy's rebuild) or, with --digest-kind bytes, a
   file digest (equal for two rebuilds). The "gxvmember" extractor
   (gxrextract.h) does the same object by object for the per-object
   derived apply, which comes with that work.

Growth and its limits (facts, for planning):

  • Every node's id, tags, stored vector and graph links stay in memory while the index is open: about 0.5 to 0.8 GB per million vectors at dimension 96 (0.51 GB int8, 0.58 GB float16, 0.78 GB float32), so a node needs a few hundred bytes of RAM whatever the disk holds.
  • Node numbers are 32-bit in memory: one file holds at most 4,294,967,280 nodes, deleted ones included (gxv_INDEX_FULL; Repair() or Merge() into a new file drops the deleted ones).
  • One writer per index file at a time (searches run beside it).
  • gxVectorSet is the way past one file and one machine's memory per file: day files or partitions, opened as needed and skipped by their day range, with at most max_open in memory at once.
  • The codec field (product quantization) and the partition fields are in the format now, so later releases can add them without a new file version.

Tests: vix_test (32-bit and 64-bit engines, crash rounds on) adds the format fields, the phase C files, gxVectorSet (recall over 5 day files against brute force, LRU 2 of 5, 1, 3 and 4 threads equal, the live file read-only and attached, missing and replaced files, bad manifests, paths with spaces), the gxvmember extractor and the rebuild from POD and real InfoHog records (logical equal to the index, two rebuilds the same bytes). The gxrepl suite adds the vector search service (remote answers equal local ones, bad requests refused, missing files, the busy cap, a copy searched under its apply lock) and a derived vector index (no .vix in the ship log, torn never TORN, the copy's rebuild logical equal to the primary's index after adds, updates and deletes with reused blocks, and byte equal to a rebuild of the primary's data).

Gxrepl fixes from the 11/12 stall (11/13/2026)

  • A request with no reply in time (or a reply that does not parse) closes its multiplexed channel and marks it broken; the set opens a fresh channel and the late reply is never read, so it can no longer shift every later request onto the wrong reply ("bad reply").
  • An apply waits for apply.jnl at most GXREPL_APPLY_LOCK_WAIT (5 s, non-blocking tries) and answers "busy", so a long derived index rebuild no longer holds back the other applies; the client retries on its next pass.
  • The derived rebuild and the ssh tunnel children run with only stdio open (close_range): they no longer inherit gxrepl.lock or ship-log state descriptors.
  • An older reader race (not from the stall fixes): the applied position is now written inside the apply lock with the pages and the seal, and the torn check re-reads a seal mismatch for up to GXREPL_TORN_RECHECK_SEC (10 s), so a promote-check no longer sees a seal ahead of the copy while an apply is in flight (test test_seal_and_position_never_split).
  • Staged unit copies: a unit's files are copied into a reflinked stage (.gxrepl/stage/<unit>/) and swapped in, commit block last, when its commit block arrives, so a link lost mid-unit leaves the copy whole at its last sealed commit; "gxrepl promote [--apply]" recovers the apply journal, finishes a begun swap and reports what was lost. Crash test hooks only with -DGXREPL_TEST_HOOKS=ON (test builds). Upgrade notes:
    • Every long-lived reader of a replicated folder (an application that keeps a copy's commit.bin or any of its data files open across a staged swap) must reopen the file when its inode changes: the swap replaces the file, so an old handle keeps reading the previous copy.
    • Failover and failback scripts should run "gxrepl promote --apply" before a node takes over, so stages left by a cut link do not block the failback.
    • Set max_message to 16 MB on both ends (gxrepl.conf). For derived sets that change all day, consider derived_delay and derived_busy_rebuild at 1800.
    • Build releases with GXREPL_TEST_HOOKS OFF (the default); only the test builds turn it on.
  • Tests: test_late_reply_never_desyncs_a_channel (the server stopped past the client timeout; the old build stays on "bad reply") and test_slow_rebuild_never_stalls_the_other_sets (another set copies during a 20 s rebuild, gxrepl's own shared holds are never reported as a local writer, the rebuild child inherits nothing of gxrepl's).

Beta 3 (11/14/2026)

  • gxrepl drain-verify, reviewed (the beta 2 fix below, plus): Every writer open gets its verify (the protocol's rule); one restart costs at most one verify and one derived rebuild.
    • no verify cascade: during a stream's verify, the open, gap and unreadable records it catches up on (at or below the position it started from, of its own log) never queue it again; one later open does, once;
    • an lsn that is not known, and "the copy's position is gone", always queue a verify;
    • the copy's position gone from the log resets it to resync, so the file sync goes on by pieces (before: "gave up after 6 tries" pass after pass);
    • a stream's log made again (purged and reopened under the same name, as osa_ingest's late pass does) is seen: the source's cached readers reopen on a new log.id, a verify running on the old log runs again, and a drain reads only the log the copy's position is on (gxReplLocal::ReadLogOf; pull mode later).
  • gxrepl: a day folder archived and reopened during a verify (osa_ingest's late pass) never seals stale data. A file update that would move the copy's position to another log queues the stream's verify again, and the seal guard applies a folder's commit block only when its stream needs no other verify (and never one of another log than the verify started on); a data file gone during its sync fails it; the source's reader reopens on log.id's content. Before, the copy could be sealed and "in step" at the source's generation with a stale data file (in the night-1 test 17 of 50 on the 7.3.x code of the .53 install).
  • gxrepl per-object derived apply (still not for production use): A1 one guarded index step (crash guard and breaker) for ApplyLog and ApplyFiles, A2, A3.

Gxrepl: a writer's open or gap record always gets its verify (11/14/2026)

The same fix as DataReel 7.3.4 (branch gxrepl-drain-verify).

  • The problem: a writer killed after its batch is committed in its journal but before the ship log has it leaves pages that the next writer's journal recovery writes into the files with no ship log record. Only the verify its open record asks for brings them to the copy, and three places applied an open or gap record without that verify: the two drains inside a file sync dropped the drain's flag, and a file update (which carries the records from the copy's position to the pieces') was applied without looking at its records' types. The copy then stayed "in step" at the source's generation and seal with stale data pages. Found by the 7.4 beta 2 test runs; in the code since gxrepl protocol 2 (11/08/2026).
  • The fix: the drain itself puts the stream on the verify list for an open or gap record and for a position gone from the log, the file sync keeps the drain's flag, and the file sync checks the records of every file update it applies. A stream that gets such a record while it is being verified is verified once more in the next pass. Each part alone covers its own path.
  • In "gxrepl once", a verify that the pass itself queued runs in a later pass, so that pass returns 1 ("not in step"): run it again.
  • gxReplClient has new members: install the library and the gxrepl binary together.
  • Tests: test_drain_verify_* (the recovered batch reaches the copy; each part alone; both parts off loses the pages; one verify per stream; a clean writer restart adds none; an open record during the stream's own verify), test_diff_pieces_against_a_racing_commit, test_position_gone_from_the_same_log_verifies. Test builds only: GXDJRNL_TEST_KILL_BEFORE_SHIP, GXREPL_TEST_SYNC_FILE_HOLD[_ON], GXREPL_TEST_DIFF_STATUS2, GXREPL_TEST_DIFF_HOLD, GXREPL_TEST_CRASH_IN_APPLY, GXREPL_TEST_NO_CALLER_VERIFY, GXREPL_TEST_NO_DRAIN_VERIFY.

Beta 4 (11/16/2026)

Replication (gxrepl) on an incremental set (derived_apply = incremental), the hardening items, and the review fixes:

  • The recovery gap: a writer's open record (its journal may have recovered a batch that has no record) or a gap record sends the stream's folders back to a rebuild and holds the stream: every batch of it is rebuilt until the stream's verify is done. The hold goes only when the client says the verify compared files (an older client, or a verify that compared none, leaves it). "gxrepl derived status" and status.json ("holds") show the holds; a hold that cannot be read goes with the next such verify, a hold whose stream was purged is reported and "gxrepl derived rebuild" removes it; a hold that cannot be written turns the set's breaker on.
  • The open record says what the writer's journal recovered (0: a clean restart, no rebuild). The static gxdJournal::Recover() leaves <journal>.recovered before it replays a batch, so a recovery done before the writer's Open() reaches the open record too; when that marker cannot be written (on any platform) it refuses to replay and keeps the journal.
  • Stamp-keeping fill: a verify's fill whose pages are all what its records write, or what the copy already holds, keeps the folder's index stamps (no rebuild); any other fill drops them.
  • Pull mode reads only the copy's own log (an older server falls back to a verify). A reader that sees the newest log segment shorter than its header (the writer is creating it) reads nothing yet instead of starting a full resync. A record bigger than max_message asks for a verify like any other, and its resyncs are bounded. The dead-folder sweep removes a folder left sealed "copying" with no database file for GXREPL_COPYING_ABANDONED_SEC (3600 s).
  • The late-pass hollow seal: a new log's verify that lists no file while its folder has database files waits until the log lists them (said once); records that would build a missing file without its first page are refused and the stream resyncs. Promote-check's stage times use localtime_r (thread safety only: no time was wrong).
  • Before turning derived_apply = incremental on, every program that journals into a replicated set and gxrepl on both nodes must run 7.4 beta 4: an older writer's static Recover() leaves no marker, and an older client's verify never clears a hold.
  • The digest fix above (FIXES AFTER BETA 3) is in beta 4.

ONE FILE LAYOUT ON EVERY PLATFORM (11/15/2026, beta 5)

Before 7.4 beta 5 the database file headers held gxUINT32/gxINT32 fields (unsigned long, long), 8 bytes on 64-bit Linux and 4 on 64-bit Windows and in 32-bit builds, so .gxd, .btx and .vix files (and record addresses) did not move between them. Now:

  • Every platform writes one layout, the canonical one: the 64-bit Linux layout. Linux files are byte for byte what 7.x and 6.x write (the files of a 7.4 beta 3 build and a beta 5 build with the same writer are identical; OSA's data files read the same). The header fields are packed explicitly (gxdbase.h: DiskLongSize(), DiskFAUSize()); the structs in memory are unchanged.
  • Files in the old 4-byte layout (written by 64-bit Windows and 32-bit builds before beta 5) are found when opened and then read AND written in that layout, so their object addresses never move: the file header, block headers, file and record locks, stats, checksums, B-tree headers and nodes, InfoHog records (object header, member count and lengths), gxPersistent strings and object headers, and the InfoHog members of vector records. A file with no block (64-bit FAU builds) cannot show its layout: canonical is taken (LayoutGuessed()); gxVectorIndex then looks for its header in the old place as well, and SetOpenLayout(4) opens one in the old layout.
  • gxd_upgrade IN.gxd OUT.gxd [--map MAP] [--records raw|infohog]: an old-layout data file rewritten as a new canonical file, only when it is run. Object addresses change (MAP lists OLD NEW), every object is read back and compared, B-tree and vector index files are refused (rebuild them from the upgraded data file).
  • SetCreateLayout(4) (or GXD_CREATE_LAYOUT=4) creates a file in the old layout, for readers older than beta 5 only.
  • A database folder copied as files (the replication_copy example) keeps the layout it has.
  • vix_test's phase C files (made on 64-bit Linux) are compared on every platform again.
  • tests/data/old_layout: files written by the 64-bit and 32-bit FAU Windows builds of beta 3; run_tests reads them with the digests Windows printed, writes them byte for byte with GXD_CREATE_LAYOUT=4, writes more to an old file (it stays old, its indexes equal a rebuild) and upgrades one.

Still per platform: the application's own record and key types. A native gx type (gxUINT32, gxINT32) or, in a 32-bit FAU build, a FAU in a record or key keeps its platform's size; use fixed-width types (uint32_t, int64_t) in records that move between platforms. The gxStream and object server message framing is one form on every platform too (see NEW IN BETA 5).

New in beta 5 (11/16/2026)

  • Object replication between Windows and Linux (gxObjRepl, gxobjrepl.h). The unique feature of 7.4:
    • Mixed Windows and Linux nodes replicate objects both ways, with the primary on either side. Takeover and rejoin work across the platforms.
    • One canonical 32-byte gxStream block header on every platform (the form 64-bit Linux always sent).
    • A peer that sends the old header with 4-byte words (Windows and 32-bit builds before beta 5) is refused with gxSOCKET_BLOCKHEADER_ERROR (PeerOldHeader()), and gxObjRepl raises an alarm.
    • Mutual TLS with each platform's own TLS library through gxSSL: OpenSSL on Linux, the Windows Schannel library on Windows.
    • From DataReel 6.4, programs built with the matching stream header can talk to 7.4 replication.
    • Tested Linux to Windows and Windows to Linux: takeover and rejoin with identical digests and index digests in every run, a 2,500-commit stress run each way, and old Windows builds refused both ways.
    • Upgrade: every node must run a 7.4 beta 5 build (see UPGRADING TO 7.4 BETA 5).
    • With the 32-bit engine each database file is limited to 2 GB (FAU_t); 1M-object stores need the 64-bit engine. Mixed 32/64-bit nodes replicate. Not tested: a 32-bit Windows build.
  • gxrepl page-shipping replication is removed. 7.4 replication is gxObjRepl.
    • A gxrepl binary installed from a 7.4 beta keeps working as it is, but it is not part of 7.4 and is no longer built.
    • The journal's ship log is gone: EnableShipLog(), DisableShipLog(), ShipLog(), EnableObjectNotes(), ApplyPages() and the "<journal>.recovered" marker. A program that called EnableShipLog() drops the call. gxdJournal::Recover() keeps its signature (its mark argument is ignored), and RecoverError() stays.
    • Also gone: gxrepl.h, gxdrepl.h, gxdstage.h, gxdstamp.h, gxrextract.h, the replication example and its pages.
    • The database digest stays, as gxDatabaseDigest() and gxDatabaseHash() (gxddigest.h) and the dr_digest tool. The values are the same as gxrepl's digest printed.
  • Fixes for every program (they came with gxObjRepl):
    • gxdJournal header salts: processes forked from one parent in the same second could write the same salt, and Recover() could then replay the previous session's records. The salt now mixes the OS random source, a fine clock, the process id and a counter. The journal format is unchanged.
    • gxDatabase::ReclaimBestFit() reuses best-fit blocks. Before, only exact fits were reused and the file grew. First fit (the default) is unchanged.
  • Fixes found by the beta 5 Windows run:
    • db_debug (gxDatabaseDebugManager::BlockSearch()) copied a block header of the file's size into the struct in memory: on Windows a canonical header is larger than the struct, so the copy overran it on the stack, and no block was ever found (the walk, search and rebuild saw an empty file). The header is now read in the file's layout. The same in the db_debug block walk (db_walk.h). A new check walks an old-layout file on Linux (layout_detect_test).
    • The imap_fetch example built on Linux only (strncasecmp).
  • Known issue of beta 4, fixed here: the library's version string (DATAREEL_VERSION_STRING, include/gxdlcode.h) still said "7.4 beta3", so beta 4's gxrepl reports 7.4 beta3. It says "7.4 beta5" now, and tools/check_release_version.sh TAG (also a run_tests check without a tag) fails when the version string, version.txt and the release notes title do not match the release.
  • gxsIMAPClient (gxsimap.h): an IMAP4rev1 mail client, based on the IMAP client class of a 2007 program that downloads report messages to a spool folder, released under the LGPL. Implicit TLS (port 993), STARTTLS (port 143), or plain text (port 143) only when asked for by name with ConnectPlain(). Login, select and examine, list mailboxes, search, fetch the header, text or whole message and the arrival time, delete and expunge, any other command, and a recorded session with the password masked. Replies are read to their own tagged completion and message data as literals, so a message can hold any text; the 2007 client's calls are kept. A server that announces LOGINDISABLED is never sent a password, and Login() on a plain text connection is refused, with nothing sent, unless the program calls AllowPlainLogin() first.
  • Example imap_fetch: search a mailbox, list the matches newest first and save each message's text to a spool folder once (from cron). Spool file names keep only letters, digits, "-", "_" and "+" of the server's arrival date, so they never leave the folder. --plain is the opt-in for a plain text login.
  • Example https_check, based on the 2007 HTTP ping and header programs: a list of web sites checked over TLS, with the status, times, size, redirects and the response headers.
  • Examples udp_broadcast and udp_multicast, based on the 2001 broadcast and multicast programs: plain (non-TLS) UDP broadcast, and IPv4/IPv6 multicast with group joins, for trusted local networks only.
  • A file of the other database engine (written with 32-bit file addresses, or with 64-bit ones) is refused with gxDBASE_FILE_ENGINE_ERROR. Before, a build with 32-bit file addresses opened a 64-bit engine's file without an error (its check compared only "GXDBASE", the start of "GXDBASE64").
  • The layout detection reads the first block's length both ways and takes the old 4-byte layout only when that length fits the file and the canonical one does not: a damaged first block is never taken for the old layout (tests/layout_detect_test).
  • The header documentation (Database Headers) explains the on-disk layout and byte order: every header field is written little endian, field by field, on every machine.
  • Tests: the IMAP client against a mock server (TLS, STARTTLS, plain text, a plain text login without the opt-in, 8-bit logins, LOGINDISABLED, message bodies that look like replies, spool names from a hostile arrival date) and against a local IMAP server in a container; gxdbmux_test (the multiplex and wire frames) in run_tests; https_check against the example HTTPS server; broadcast and multicast on this host.
