Overview

The gxRDBMS class is a small relational database manager. It stores the records of one table in a data file and keeps one or more index files used to find records quickly. The data file is created by the 32/64-bit database engine. The index files are B-tree files. Both kinds of file are opened and managed through a POD (Persistent Object Database) manager that the gxRDBMS object owns.

The relational layer is made up of four headers. The "gxrdbms.h" header declares the gxRDBMS class and a few standalone process ID file functions. The "gxrdbhdr.h" header declares the type definitions, constants, field types and the helper classes used by gxRDBMS: the file header (gxRDBMSHeader), the record header (gxrdRecordHeader), the persistent table header (gxrdTableHeader and gxrdTableHeaderField), the in-memory record (gxrdDatabaseRecord), the table (gxrdDatabaseTable), the field exclude list (gxrdExcludeFields) and the B-tree key (gxrdDatabaseKey_t and gxrdDatabaseKey). The "gxrdbdef.h" header declares functions that read table, key and other definitions from a text definition file. The "gxrdbsql.h" header is reserved for future SQL functions and declares nothing.

A table is described by two strings. The table definition names the table and lists its fields. The key definition says which field is the primary key, which fields are secondary keys, and sets a few options. You pass both strings to gxRDBMS::CreateTable(). This call parses the strings, builds the file names, and creates or opens the data and index files. You then build gxrdDatabaseRecord objects from the table's record definition and pass them to the add, find, change and delete functions.

Tables, Fields and Keys

Tables. Each gxRDBMS object works with one table. The table name is used to build the data and index file names, so it may not contain any of these characters: / \ * | : " < > ?. Every record written to the data file starts with a record header. The record header holds a table ID, which is the CRC-32 of the table name, and the number of fields.

Fields. A table has at least one field. The table header can hold up to 255 fields (tableMAX_FIELDS), but the definition string parser stops at 255 comma separated words, and the first word is the table name, so a table definition can describe at most 254 fields. Each field has a name, a display column length, a type, an optional array length and an optional format specifier. The field types are listed in the gxrdFIELD_TYPES enumeration. In memory, each field of a gxrdDatabaseRecord is held in its own MemoryBuffer as a one byte type ID, a four byte length and the field data. This lets a field grow or shrink without moving the other fields. On disk, the fields are written one after another after the record header, in the same type, length and data form.

Field numbers. Field numbers are not used the same way everywhere. The gxrdDatabaseRecord functions use zero-based column numbers. The key definition string uses one-based column numbers ("COL 1" is the first field). The gxRDBMS::Search() and gxRDBMS::SortOrderList() functions take one-based field numbers. The gxRDBMS::Find() function takes a zero-based field number. In several places the value -1 means "all fields".

Keys. A key is not the field value itself. A key is a 32-bit CRC of the key field data, made by gxrdDatabaseRecord::CreateKey(). If no primary key column is given ("PRI: COL NONE"), the key is the CRC of all fields. String fields are converted to upper case before the CRC is made when case is ignored. Each B-tree entry stores the key CRC, the table ID and the block address of the record in the data file. Because keys are CRC values, the B-tree is ordered by CRC and not by field value. Two different values can have the same CRC. When duplicates are not allowed, only one of them can be stored. NOTE: 10/14/2026: Fixed: a record found through its key is now read and its key fields are compared with the search record, so a value with the same CRC is no longer reported as found or deleted.

Table Definitions

A table definition is a comma separated string. The first word is the table name. Each word after that defines one field, in this form:

FieldName{ColumnLength}TYPE[ArrayLength].FormatSpecifier

The parts are:

FieldName - The name of the field. It is stored in the table header. Names longer than 254 characters are cut short so that the stored name always ends with a null.
{ColumnLength} - Required. The number of characters used to display the field. A column length of 0 tells a user interface to hide the field. A word without both braces is rejected with gxDBASE_BAD_COL_LENGTH.
TYPE - Required. One of CHAR, INT16, INT32, INT64, FLOAT, BOOL, VCHAR, BINARY, BLOB, CURRENCY or DATE. The name must be in upper case. An unknown type is rejected with gxDBASE_BAD_FIELD_TYPE.
[ArrayLength] - Optional. The number of elements. The field data size is the type size times the array length. For CHAR and VCHAR fields the type size is one byte, so "CHAR[64]" reserves 64 bytes. Without an array length a CHAR, VCHAR, BOOL, BINARY or BLOB field starts with one byte.
.FormatSpecifier - Optional. A number or a single letter that tells an application how to show the field. If the text after the dot is a non-zero number, the number is stored. Otherwise the first character is stored. See the format specifier constants.

Leading and trailing spaces around each word are removed. Escape sequences in the table name that start with "%" are converted and tab characters are removed. The table definition below defines a table named "contacts" with three fields:

contacts, Name{30}VCHAR[64], Phone{15}CHAR[16], Age{3}INT32

When the table definition is parsed by gxrdDatabaseTable::CreateTable(), the table builds a shorter record definition that keeps only the table name, the types and the array lengths. The record definition for the table above is:

contacts,VCHAR[64],CHAR[16],INT32

Records are created from the record definition. The record definition string is also used to test that a record belongs to the table. The gxRDBMS write, delete and change functions reject a record whose record definition is not exactly the same string (gxDBASE_BAD_RECORD).

Key Definitions

A key definition is a comma separated string parsed by gxRDBMS::DefineKeys(). The words are not case sensitive. The string must contain "PRI". The words are:

PRI: COL n          Primary key is field n (one-based).
PRI: COL NONE       The primary key is made from all the fields.
SEC: COL n          Field n is a secondary key. Repeat for more secondary keys.
ATTRIB: NOCASE      Ignore string case when keys are made and compared.
ATTRIB: ANCOMPARE   Use alphanumeric string compares.
ATTRIB: ALLOWDUP    Allow duplicate keys. The block address is then part of the key. Records with the same key values can be added, and a lookup by key returns the first record whose key fields match (10/24/2026, version 6.0).
ATTRIB: ORDER=n     Set the B-tree node order (default 64).
ATTRIB: RECLAIM=x   Set the deleted block reclaim method: NONE, BEST or FIRST.

Each ATTRIB word sets one attribute. Any other ATTRIB word, a PRI or SEC word without "COL", or a column number of 0 makes the call fail with gxDBASE_BAD_KEY_DEF. For example:

PRI: COL 1, SEC: COL 2, ATTRIB: NOCASE, ATTRIB: RECLAIM=BEST

The gxRDBMS constructor sets the stored key definition string to "PRI: COL 1,ATTRIB: NOCASE, ATTRIB: ANCOMPARE". This string is not parsed by the constructor. If you create a table with gxRDBMS::Create(), which does not take a key definition, the key settings stay at the constructor defaults: the primary key is made from all fields, case is compared, and there are no secondary keys. The default string is still written to the table header.

Definition Files

The functions in "gxrdbdef.h" read definitions from a text file. Each definition is a block that starts with a tag line and ends with "};". Lines that start with "#" and blank lines are skipped. Leading and trailing spaces are removed from each line and the lines in a block are joined with no separator, so each field must end with a comma. Everything up to and including the first "{" and everything from "};" on is removed. The tags are "DEFINE TABLE", "DEFINE KEYS", "DEFINE FORM", "DEFINE FKEYS", "DEFINE USER ACCESS" and "DEFINE GROUP ACCESS". The tag search does not depend on case. A short definition file looks like this:

# Contacts table
DEFINE TABLE {
  contacts,
  Name{30}VCHAR[64],
  Phone{15}CHAR[16],
  Age{3}INT32
};
DEFINE KEYS {
  PRI: COL 1,
  ATTRIB: NOCASE
};

The block must have a "{" on or after the tag line and before the first field, because the first "{" in the joined text is treated as the start of the block.

Adding, Finding, Changing and Deleting Records

Creating a record. Construct a gxrdDatabaseRecord from gxRDBMS::RecordDef(). Set each field with gxrdDatabaseRecord::SetField(), using zero-based column numbers. SetField() copies the bytes you give it and changes the stored field length to that number of bytes, so a string field should include its null terminator if you want it stored.

Adding. gxRDBMS::AddRecord() first looks for the record's primary key and then each secondary key. If any key is found the record is not added and the data file error is set to gxDBASE_RECORD_EXISTS. Otherwise gxRDBMS::Write() stores the record in one block of the data file and inserts the primary key into B-tree 0 and each secondary key into B-tree 1, 2, and so on. If a key cannot be inserted, the data file block is deleted again.

Finding. gxRDBMS::FindRecord() builds the keys from the record you pass in, searches the indexes, and passes back the block address of the record. By default it also reads the record from disk into the object you passed in. Only the key fields of the search record need to be set.

Changing. gxRDBMS::ChangeRecord() takes a "from" record that identifies the existing record and a "to" record with the new values. If the two records are the same size on disk the block is overwritten in place. Otherwise the old record and its keys are deleted and the new record is written to a new block. When any primary or secondary key value changes, the keys are deleted and added again. gxRDBMS::ChangeOrAdd() does the same but adds the "to" record when the "from" record is not found. gxRDBMS::ChangeRecordField() changes a single field of the record at a known block address.

Deleting. gxRDBMS::DeleteRecord() finds the record by its keys, removes the primary and secondary keys from the B-trees, and deletes the data file block. Deleted blocks are reused according to the reclaim method (first fit by default).

Errors. Most functions that return int return 1 (true) for success and 0 (false) for failure. Functions that return gxDatabaseError return gxDBASE_NO_ERROR (zero) for success. In both cases the error code is usually also stored in the POD object. Use gxRDBMS::GetDatabase() with POD::GetDataFileError() or POD::GetIndexFileError() to read it.

Indexes and B-trees

All tables use at least one index. Index number 0 always holds the primary key. When the key definition has a primary key column and one or more secondary keys, there is one more index for each secondary key, in the order the SEC words appear. If the primary key is "COL NONE", secondary keys are parsed but no secondary indexes are made.

With a single index the index file name is the table name plus the index file extension, for example "contacts.gix". With secondary keys each index is a separate file and a number is added to the name, starting at 1: "contacts.gix1" holds the primary key, "contacts.gix2" the first secondary key, and so on. The data file name is the table name plus the data file extension, for example "contacts.gxd". If a directory is given, it is put in front of each name. When the tables are opened and some but not all of the index files exist, or the data file does not exist, the existing index files are removed and created again.

The B-tree key type is gxrdDatabaseKey. All indexes use the same key type and node order. The index files are only an aid to searching. They can be checked with CheckIndex() and VerifyIndex() and rebuilt from the data file with RebuildIndex(). Search() and SortOrderList() walk one B-tree, read each record from the data file, and put the records they keep into an in-memory gxBStree list. That list is ordered by the primary key field, compared by value, not by CRC.

File Layout

The data file reserves a static area just after the database engine file header. Its size is returned by gxRDBMS::HeaderSize(). The static area holds, in order: the gxRDBMSHeader file ID ("GXRDBMS", a revision letter and a version number), the table name, the key definition, the form definition, the foreign key definition, the number of fields, one gxrdTableHeaderField for each field, and an application space of tableAPPLICATION_SPACE bytes. The table header is written when a new data file is created. When an existing file is opened and the field names, lengths or format specifiers in the file do not match the table definition, the header is written again from the definition. Each record is stored in its own data file block: a gxrdRecordHeader followed by the fields.

Usage Example

No program in this repository uses gxRDBMS, so the example below is a minimal program written for this page. It only calls functions declared in these headers.

#include <iostream>
#include "gxrdbms.h"

int main()
{
  gxRDBMS db;
  gxString tdef = "contacts, Name{30}VCHAR[64], Age{3}INT32";
  gxString kdef = "PRI: COL 1, ATTRIB: NOCASE";

  // Parse the definitions and create or open contacts.gxd/contacts.gix
  gxDatabaseError err = db.CreateTable(tdef, kdef);
  if(err != gxDBASE_NO_ERROR) {
    std::cout << gxDatabaseExceptionMessage(err) << "\n";
    return 1;
  }

  // Build a record from the table's record definition and add it
  gxrdDatabaseRecord rec(db.RecordDef());
  gxINT32 age = 42;
  rec.SetField("Alice", 6, 0);           // Zero-based column 0, with the null
  rec.SetField(&age, sizeof(age), 1);
  if(!db.AddRecord(&rec)) {
    std::cout << "Record not added\n";
  }

  // Find it again. Only the key field needs to be set.
  gxrdDatabaseRecord found(db.RecordDef());
  found.SetField("ALICE", 6, 0);         // NOCASE: case does not matter
  FAU_t block_address;
  if(db.FindRecord(&found, block_address)) {
    std::cout << (char *)found.GetField(0) << "\n";

    // Change the age
    gxrdDatabaseRecord changed(found);
    gxINT32 new_age = 43;
    changed.SetField(&new_age, sizeof(new_age), 1);
    db.ChangeRecord(&found, &changed);

    // Delete the record
    db.DeleteRecord(&changed);
  }

  db.Close();
  return 0;
}

FAU_t gxRDBMS::Find(gxrdDatabaseRecord *r, __ULWORD__ field, int case_cmp, int alpha_cmp, int test_tree)

Low-level public member function used to find a record. "field" is a zero-based column number, or -1 for all fields. If the key definition gives this field a B-tree, a key is made from the field and that B-tree is searched. The record the key points to is then read and its key field is compared with "r". NOTE: 10/24/2026: Fixed in version 6.0: with duplicates allowed the block address is part of each key, so the search key, which has a block address of 0, never matched and every lookup by key failed. FindRecord(), DeleteRecord() and the change functions could not find any record. Find() now starts at the first key with the same CRC-32 value and reads each record with that value until one matches.
