DataReel 7.5 Release Notes (the Python module), 11/26/2026

DataReel 7.5 adds the datareel Python module, a package that installs with pip. It is built from this repository (python/) on top of 7.4.1, so everything in 7.4.1 is in it (RELEASE_NOTES_7.4.txt, "NEW IN 7.4.1"). The file formats are those of 7.4; the gxStream and gxObjRepl wire formats are those of 7.4 with new fields at the end of the replication hello (7.4.1 and 7.5 nodes work together).

DataReel 7.5 is the main, fully supported release. 7.4.1 is the previous 7.x release; 6.4.2 is the legacy release (bug fixes and security updates only).

NEW IN 7.5 (tag 7.5, 11/26/2026)

7.5 is the 7.5 beta 3 patch 2 code, released with version 7.5. The sections below list what each beta added. In short:

  • The datareel Python module (pip package datareel 7.5, wheel datareel-7.5-cp312-cp312-linux_x86_64.whl for Linux x86_64 and CPython 3.12, RHEL 9 and 10): read gxObjRepl nodes from another process (Reader), write them as a gxObjRepl primary (Primary), run a copy (Copy), and take over, rejoin, check and swap nodes, all working with C++ nodes; the database layer (Database, BTree, Journal); vector index files (VectorIndex, create_vector_index(), merge_vector_indexes()); gxStream over TLS (Stream, StreamServer) and the object service client (ObjectClient).
  • gxObjRepl (C++ and Python): the incremental rejoin (only the objects either node changed after a split are sent), the schema check (refused rejoin between nodes with different record layouts, then rebuild and objrepl swap), index_check by index name, and the objrepl options --schema, --rejoin-max-share and --drain-secs.
  • The user's manual (python/docs/users-manual.md) with 14 examples, the build guide (python/docs/building.md), python/AGENTS.md and the AI-assisted guide (docs/ai/python.md).
  • gxObjReplReader::Ids() (Python Reader.ids() with no after/limit) reads the id index in pages of 16384 keys, each page under the journal read lock, so a whole walk of a large database no longer holds up the node's commits. On a 2M-object node, one commit used to wait 5.1 s for the walk; now the slowest commit waits 0.48 s, and the walk takes 3.5 s instead of 6.9 s. A database that fits in one page is still read at one commit. On a larger one, an object added or removed during the call may or may not be listed. (OSA report 1.1.) Also: test_objrepl_stall.sh has a new 'idle drops' case confirming the 7.4.1 CLOSE-WAIT fix, and KNOWN_ISSUES.md lists slow copy index builds on slow disks and key-order scan speed.
  • Windows: prebuilt static libraries again, as for 7.4.1: datareel-7.5-windows-x64-schannel.zip (64-bit database engine) and datareel-7.5-windows-x86-schannel.zip (32-bit engine), release builds with Visual Studio 2026 (/MT, native Schannel TLS) and a CMake package (find_package(DataReel)). Still no Windows Python wheel.
  • Documentation for 7.5: the security and the gxStream and replication white papers (the incremental rejoin, the 7.5 hello fields, the Python package), the port 2073 protocol specification draft-gaer-datareel-gxstream-01 (docs/rfc/: the optional hello fields and the frames F_RJ_SET, F_RJ_BATCH and F_RJ_END; -00 is kept), the replication administrator's guide, the AI-assisted guides and the benchmarks page.
  • Package version 7.5; library version "7.5".

Upgrading from 7.4.1

  • C++ programs build against 7.5 unchanged. Existing database, index, vector and journal files open as they are.
  • Replication: upgrade the copy first, then switch, then upgrade the old primary (replication administrator's guide, section 5). 7.4.1 and 7.5 nodes replicate with each other in both directions. The incremental rejoin needs 7.5 on both nodes: with an older primary a rejoin is a full send, as before, and a node that took over with an older build makes its first rejoin after the upgrade a full send.
  • Python programs written against a 7.5 beta: install the 7.5 wheel over the beta. Since beta 3 patch 2, databases() leaves out names starting with "_" (databases(hidden=True) lists them).

New in 7.5 beta 3

  • The incremental rejoin (gxObjRepl, C++ and Python): when both nodes wrote after a split (a standby took over while the old primary kept writing, the OSA emergency path), objrepl rejoin / datareel.rejoin() keeps the old primary's data and the list of objects its unacknowledged commits changed. The new primary checks that the two histories match at the seq it took over at (ROOT/epochs, written at each takeover) and sends only the objects either node changed since then (its change list, ROOT/objrepl.changes.gxd), then its digest log past the split: equal digests, with no full send. A full send instead when the histories differ, when the change set is more than rejoin-max-share percent of the objects (default 50), or with objrepl rejoin --full / datareel.rejoin(root, incremental=False). A node killed in the middle keeps waiting and finishes on the next connect.
  • The schema check: a fingerprint of the index spec, the link map and the new "schema" setting (the application's record layout version, such as news-v3) goes with the hello. An incremental rejoin between nodes whose fingerprints differ is refused, with what differs; the node keeps its data and is rebuilt instead: a new copy in an empty folder takes a full send, then objrepl swap OLD NEW / datareel.swap(old, new, index) puts it in place and keeps the old folder as OLD.before-rebuild-DATE (gxObjRepl::Swap). In the running stream a difference is a warning.
  • Status: last_rejoin (incremental or full send) and last_rejoin_objects on the primary. objrepl: --schema, --rejoin-max-share, --drain-secs (the generator's final drain).
  • Wire: new fields at the end of the hello and its reply, and frames F_RJ_SET, F_RJ_BATCH and F_RJ_END. 7.4.1 and 7.5 beta 2 nodes work with beta 3 nodes as before (tested both ways).
  • Tests: utils/objrepl/test_objrepl_rejoin.sh (the emergency path and back, the schema refusal, rebuild and swap, another history, the share limit, --full, a node killed inside a batch and inside the end, and with OBJREPL_OLD_BIN a 7.4.1 node both ways), and Python tests: a C++ production primary and a Python DEV copy that detaches and writes, the rejoin and the roles going back; a Python primary under a C++ new primary; the schema refusal, rebuild and swap from Python.

New in 7.4.1 (11/20/2026)

  • gxObjRepl uses port 2073 by default: replication is a gxStream object stream, and 2073 is the gxStream port registered with IANA (gxs-data-port). A copy with no "listen" port listens on 2073, and a primary whose "copy" setting has no port connects to 2073 (gxObjReplConfig::listen_port is 2073, copy is HOST[:PORT]). "listen ADDR" sets only the address. Configs that name a port work as before; a bad copy or listen value is refused at start. utils/objrepl/test_objrepl_config.sh checks both (it needs 127.0.0.1:2073 free).
  • Security fix, the object service (gxdbobject.cpp): an address a client sends must be the start of a normal (not deleted) block inside the file, and for a writable database one of its live objects (the server keeps the list, made when the database opens). 7.4 checked only the check word of the block header in front of the address, so a client allowed to write could copy a block header into its own object and CHANGE or DELETE at the address behind it, writing past that object into the next ones; REQUEST could read past an object or read deleted blocks. Only clients that passed mutual TLS and the allow list could do it. tests/object_service_test.cpp (19 checks, 10 of them fail on 7.4) runs in run_tests.sh.
  • gxObjRepl fixes (11/19/2026), seen with a copy on a slow disk: utils/objrepl/test_objrepl_stall.sh (a test build: -DGXREPL_TEST_HOOKS=ON) fails on 7.4 and passes on 7.4.1.
    • The primary's Pump() could wait in a socket read for 10+ minutes. One exchange (a frame and the copy's answer) now has a total deadline, the new ack-timeout setting (default 300 s; objrepl --ack-timeout S). Past it the connection is shut down and dropped and Pump() returns. The connect and handshake take at most 30 s, or ack-timeout when that is less.
    • The copy served one connection at a time and did not watch its listener, so the primary's new connections waited unaccepted (CLOSE-WAIT, the TLS hello unread) until the old connection went idle for idle-timeout seconds. The copy now takes a new connection that passes the TLS client check at once and drops the old one; one that fails the check is closed.
  • New: gxObjReplReader (gxobjrepl.h), read-only access to a node's databases from other processes while the node runs (gxObjRepl holds a node folder for one process). Get, IsLive, Ids, Databases, FindKey and Nearest, each under the node journal's shared lock, so a call sees whole commits only; Seq() names the commit read. A call opens and closes the files it needs; a loaded vector index stays in memory and is read again when the node moves on. The 64-bit engine only. utils/objrepl/test_objrepl_reader.sh.
  • gxdJournal: SetWriteLock(1) now covers write-back mode as well (WriteCommitted() and checkpoints), and Recover() holds the lock while it replays, so a gxdJournalReadLock reader never sees a batch half written. gxObjRepl nodes turn the write lock on.
  • KNOWN_ISSUES.md: the known limits, untested areas and flaky tests.
  • Documentation: docs/security_white_paper.md, the security design of the library; docs/gxstream_replication_white_paper.md, gxStream and replication on port 2073; docs/rfc/draft-gaer-datareel-gxstream-00, the protocol's specification (an Internet-Draft for the Independent Submission stream, which also covers the DataReel 6.x legacy transports).

Phase a (11/12/2026): vector index file, exact search

New headers gxvindex.h (gxVectorIndex, gxvFilter, gxvResult) and gxvkern.h (distance kernels); sources src/gxvindex.cpp and src/gxvkern.cpp; test program utils/vix_test.

1. gxVectorIndex keeps vectors in a ".vix" file, which is an ordinary

   gxDatabase file: a 256-byte static area (magic "GXVIX74", version,
   dimension, element type, metric, M / M0, ef_construction, node
   size, entry node, counts and a 63-character spec) and one
   fixed-size block per node (64-bit object id, flags, level, four
   32-bit tags, upper-level block, neighbor slots, vector). The graph
   of phase B uses the neighbor slots already reserved in every node,
   so phase A files open unchanged later.

2. Insert / Update / Delete (a tombstone) / Get / Contains, each a few

   writes to the file. Attach the index to a gxdJournal with
   j.Attach(vix.Database()) and a commit carries an object, its B-tree
   keys and its vector together; Rollback() then Reload().

3. Exact(query, k, results, filter): the k nearest live nodes, sorted

   by distance then id. gxvFilter tests tag ranges (equality is a
   range of one, so session, kind and a date upper bound are all
   tags) and an optional accept callback. (Search() was Exact() until
   phase B.)

4. Metrics: squared L2, cosine (vectors stored unit length, distance

   1 - cosine) and inner product (minus the dot product). Float32
   only in phase A; float16 and int8 come in phase C. Dimension 1 to
   4096. NaN and infinite values are refused.

5. Spec guard: Create(..., spec) stores a text such as

   "anomaly/shock/v1/<builder hash>"; Open(name, mode, spec) refuses a
   file with another spec, so vectors from a different feature
   builder never mix in one index.

6. Concurrency: the ids, tags and vectors stay in memory while the

   index is open, so searches never read the file. Searches share a
   lock; writers take it exclusively and go ahead of new searches
   (writer preference), so steady searching never stalls inserts.

7. Kernels: 8 partial sums in a fixed order, the same on the SSE2

   path and the plain C path (bit-identical results); plain C-style
   functions so the 6.x version shares them word for word.

8. Verify(resolve, data, bad, report) compares the file with memory

   and asks the caller whether each node's object still exists.

Tests (vix_test, 32-bit and 64-bit database engines): kernels against the written-out order; Exact against a brute-force reference for all three metrics with tag, range and callback filters and equal-distance order; create / insert / update / delete / reinsert / reopen / read only / spec mismatch / bad files; journal commit and rollback; three reader threads searching during 20,000 inserts and deletes (clean under ThreadSanitizer); 45 kill -9 rounds during committed batches: every round recovered exactly the committed batches, never a partial one.

Measured (4-core VM, dimension 79, k = 20): insert about 5 us; exact search of 30,000 vectors 0.9 ms p50, 150,000 6.7 ms, 1,000,000 55 ms (memory bound); opening 1,000,000 nodes 2.3 s. Sub-millisecond search over large sets is phase B's graph.

Phase b (11/12/2026): hnsw graph search, merge, repair

1. Search(query, k, results, ef, filter) walks an HNSW graph kept in

   the neighbor slots of each node plus an upper-level block for the
   nodes above level 0. A node's level is an integer hash of its id,
   so the same inserts in the same order build the same graph on every
   node. Up to 4096 nodes, and for filters (or tombstones) that leave
   fewer than about 5% of the nodes, Search() is Exact().

2. Filtered graph search: every node is a stepping stone, only live

   nodes that pass the filter are results.

3. Live inserts: Insert() works out its links under the shared lock

   (searches keep running), writes the file, then takes the exclusive
   lock only to link the node (microseconds). Per-node arrays grow in
   fixed chunks, so growing never copies what is there.

4. Update() with the same vector rewrites the tags in place; with a new

   vector it deletes the node and inserts a new one in one step.
   Deleted nodes stay in the graph until Repair().

5. Repair() rebuilds the graph from the live nodes and writes it.

   Merge(out, inputs, spec) builds one index from many files (the day
   files of a month): same dimension, metric and spec, ids unique
   across them, tombstones left out, every link written once.

6. Phase A files open unchanged: the graph is built in memory at Open()

   (GraphSaved() = 0) and Repair() saves it. A damaged link in a saved
   graph is handled the same way. Verify() also checks every link
   against the file.

7. Fix: the 256-byte header was written at FAU 256 (gxDatabase

   StaticArea() returns the static area's size, not its address), so
   the first node block overlapped header bytes 96-255. It now sits at
   FileHeaderSize(). Phase A was never installed, so no file has the
   old layout.

Tests (vix_test, 32-bit and 64-bit database engines, 11,897 checks): recall against Exact for all three metrics (20,000 clustered vectors: 1.000 / 1.000 / 0.996 at ef 64), filtered recall, a selective filter equal to Exact, the graph read back from the file gives the same answers, the same inserts build the same graph, deletes (no deleted node returned) and updates, Repair(), a phase A file and a damaged link rebuilt and repaired, Merge() of three day files (and its refusals), 45 kill -9 rounds on each engine (all recovered exactly, Verify() clean including every link), three searchers during 20,000 inserts and deletes, clean under ThreadSanitizer.

Gate (vix_test --gate 1000000, 4-core VM, dimension 96, M 16, ef_construction 200, k 20; one thread inserting in journal batches of 100 while three threads search):

  • Clustered vectors (1000 centers, like real features): build 526 s (0.5 ms an insert); quiet ef 64 recall 0.987, p50 0.17 ms, p99 0.34 ms; live: 1,053 inserts a second during 425,758 searches, p50 0.18 ms, p99 0.61 ms (p99.9 1.4 ms); recall after 0.986; ef 128 recall 0.999 at p99 0.53 ms. Gate met.
  • Uniform random vectors (pure noise, the worst case for any graph index): p99 0.84 ms live but recall only 0.23 at ef 64; at 50,000 nodes ef 64 / 256 / 1024 give 0.58 / 0.88 / 0.99. Noise has no near neighbors to find; real feature vectors are not like this, but a feature builder whose vectors look like noise needs a larger ef or Exact().
  • Opening the 1,000,000-node file (nodes and graph): 8.6 s.

Build fix (11/12/2026, found on RHEL 10): GCC fuses a*b + c into one multiply-add (FMA) instruction on x86-64-v3, RHEL 10's baseline, which changed the last bit of some distances and failed vix_test's bit-exact kernel check. gxvkern.cpp and vix_test.cpp now turn contraction off with a pragma, and the CMake files also build them with -ffp-contract=off. The crash test now waits until the child has created and synced the file before it starts the kill timer, so a slow machine no longer kills the child before its first commit.

Phase c (11/12/2026): float16 and int8 vectors, vector members

1. Element types gxvFLOAT16 and gxvINT8 (types 2 and 3 in the header).

   A node stores its vector as a code: float32 4 * dim bytes; float16
   2 * dim bytes (IEEE binary16, round to nearest even, subnormals
   kept); int8 dim signed bytes and a float32 scale per vector
   (s = max|v| / 127, q = clamp(lrintf(v / s), -127, 127), each value
   within s / 2). Node size = 48 + 8 * M0 + the code bytes; the header
   check follows the type. gxvFLOAT32 files are byte-identical to
   before (no version change); a library that does not know a type
   refuses it with gxv_UNSUPPORTED.

2. gxvCOSINE vectors are normalized, then stored. Every distance, in

   inserts as well as searches, uses the decoded vector, so Insert(),
   Repair() and Merge() build the same graph (vix_test checks it for
   every type and metric). Queries are not rounded. Get() returns the
   decoded vector; Update() compares stored codes.

3. float16 values above 65504 in size are refused with the new error

   gxv_OUT_OF_RANGE (added at the end of gxvError).

4. gxvkern.h: gxv_f16_from_float(), gxv_float_from_f16(),

   gxv_i8_encode(), gxv_i8_decode() (plain C, for the 6.x version).

5. Vector members: a record carries its vector in the index's stored

Growth and its limits (facts, for planning):

  • Every node's id, tags, stored vector and graph links stay in memory while the index is open: about 0.5 to 0.8 GB per million vectors at dimension 96 (0.51 GB int8, 0.58 GB float16, 0.78 GB float32), so a node needs a few hundred bytes of RAM whatever the disk holds.

ONE FILE LAYOUT ON EVERY PLATFORM (11/15/2026, beta 5)

Before 7.4 beta 5 the database file headers held gxUINT32/gxINT32 fields (unsigned long, long), 8 bytes on 64-bit Linux and 4 on 64-bit Windows and in 32-bit builds, so .gxd, .btx and .vix files (and record addresses) did not move between them. Now:

  • Every platform writes one layout, the canonical one: the 64-bit Linux layout. Linux files are byte for byte what 7.x and 6.x write (the files of a 7.4 beta 3 build and a beta 5 build with the same writer are identical; OSA's data files read the same). The header fields are packed explicitly (gxdbase.h: DiskLongSize(), DiskFAUSize()); the structs in memory are unchanged.
  • Files in the old 4-byte layout (written by 64-bit Windows and 32-bit builds before beta 5) are found when opened and then read AND written in that layout, so their object addresses never move: the file header, block headers, file and record locks, stats, checksums, B-tree headers and nodes, InfoHog records (object header, member count and lengths), gxPersistent strings and object headers, and the InfoHog members of vector records. A file with no block (64-bit FAU builds) cannot show its layout: canonical is taken (LayoutGuessed()); gxVectorIndex then looks for its header in the old place as well, and SetOpenLayout(4) opens one in the old layout.
  • gxd_upgrade IN.gxd OUT.gxd [--map MAP] [--records raw|infohog]: an old-layout data file rewritten as a new canonical file, only when it is run. Object addresses change (MAP lists OLD NEW), every object is read back and compared, B-tree and vector index files are refused (rebuild them from the upgraded data file).
  • SetCreateLayout(4) (or GXD_CREATE_LAYOUT=4) creates a file in the old layout, for readers older than beta 5 only.
  • A database folder copied as files (the replication_copy example) keeps the layout it has.
  • vix_test's phase C files (made on 64-bit Linux) are compared on every platform again.
  • tests/data/old_layout: files written by the 64-bit and 32-bit FAU Windows builds of beta 3; run_tests reads them with the digests Windows printed, writes them byte for byte with GXD_CREATE_LAYOUT=4, writes more to an old file (it stays old, its indexes equal a rebuild) and upgrades one.

Still per platform: the application's own record and key types. A native gx type (gxUINT32, gxINT32) or, in a 32-bit FAU build, a FAU in a record or key keeps its platform's size; use fixed-width types (uint32_t, int64_t) in records that move between platforms. Replication fixes

1. Seal per folder. A copy's unit seal is now "log G L S C": C is the

   ship log record that last changed that folder, while L stays the
   stream's applied position. Derived indexes (derived = GLOB, stamped
   in <folder>/derived.stamp) are compared with C, both in "gxrepl torn"
   and in the {lsn} that derived_rebuild is given.
   Before, every record of a stream moved L in the seals of all of the
   stream's folders, so the indexes of folders that had not changed
   looked stale and were rebuilt again and again. In production that was
   most of about six rebuilds an hour, each under the apply lock.
   - A seal without C (written by 7.3.2) reads as C = L. After an
     upgrade, each folder is rebuilt once and then keeps its indexes.
   - A 7.3.2 gxrepl reads a 4-field seal and ignores C.
   - These all set C to the record that made the change:
     - a verify repair, including a size-only change;
     - a delete of a data file;
     - a new log under the same stream name;
     - a fill.
     Two streams' numbering is never mixed.

2. A delete's reseal comes first. When a data file of a log-sealed

   folder is deleted, the seal is rewritten with C = L before the file
   is unlinked. This happens under the apply lock, after any pending
   journal batch is recovered. A crash in between costs one extra
   rebuild, never a stale index.

3. A verify sees files named during its pass. The client read each

   stream's file list once per pass. If a stream named a new file (a
   new unit's commit block) while its verify ran, that file was not
   verified, and the unit could stay "copying" until the next verify.
   The list is now read again after a stream's verify, and the stream is
   verified again in the same pass if files joined it (at most 3 times).

4. "gxrepl torn" (promote-check) reads each unit under a shared lock on

   the set's apply.jnl.
   - The lock is taken per unit, only around that unit's small reads:
     commit block, seal, applied position, derived state and stamp.
     Nothing is hashed under it. Measured on production sets, the
     longest hold was 0.054 ms.
   - While it holds the lock no apply is in flight, so the timed
     re-reads are not needed.
   - The waits share a budget per set, GXREPL_TORN_LOCK_WAIT (default
     15 s). Past it, the rest of the set is read unlocked with the old
     re-reads and a WARNING line; the exit code is unchanged.
   - GXREPL_TORN_LOCK_STATS=1 prints the lock counts and hold times.
   - gxReplTornLockStats and a 4-argument gxReplTornCopies are new. The
     old signatures are kept.

5. ApplyFiles writes the streams' applied positions inside the apply

   lock, after any staged swap, as ApplyLog has done since 7.3.2. Before,
   the positions were written after the lock was released, while the
   batch's "log G L" seals were already written. Even a locked reader
   could then see "sealed at record L, the copy applied up to L-1" (a
   false TORN).

Replication fixes

1. Channels resync after a timeout. A channel whose request had no

   reply in time, or whose reply did not parse, is now closed and
   marked broken (gxReplRemote::ChannelBroken), and the set's thread
   opens a fresh channel. Before, after a network outage every set
   read the previous request's late reply ("bad reply") until the
   client was restarted.

2. The apply lock is bounded. An apply takes apply.jnl with a bounded

   wait (GXREPL_APPLY_LOCK_WAIT, default 5 s) and answers "busy"
   instead of blocking behind a long derived index rebuild, so a slow
   rebuild never stalls the other sets.

3. Derived index rebuild and ssh tunnel children start with only

   stdin, stdout and stderr open (no inherited sockets or locks).

4. The seal, the commit block and the applied position are never read

   split. ApplyLog writes a stream's applied position inside the same
   apply.jnl transaction as the records' pages and the unit seal, and
   "gxrepl torn" (promote-check) re-reads a seal that does not match
   the applied position for up to GXREPL_TORN_RECHECK_SEC (10 s), so
   an apply in flight is not reported as torn. Before, a promote-check
   run during steady commits could report "sealed at record N, the
   copy applied up to N-1".

5. Staged unit copies. A unit (a folder with a commit block) that must

   be copied whole is now written into a reflinked stage
   (<set root>/.gxrepl/stage/<unit>/) and swapped in when its commit
   block arrives: the commit block is marked odd, the data files are
   renamed in, then the commit block lands. A lost link part way
   through a copy leaves the copy whole at its last sealed commit
   instead of torn. A stage is used only by the copy that began it, is
   reused for the same generation, and is skipped (the copy is made in
   place, as in 7.3.1) for ship-log sets, a unit with no copy yet, an
   unsealed unit, a unit over stage_max_bytes (16 GiB), a file system
   without reflinks (FICLONE), or when the stages of all sets would
   leave too little free space.

6. gxrepl promote [--apply]. Run on a copy before it takes over as the

   writer: it recovers apply.jnl, finishes a swap that was begun,
   discards the other stages and says what each discard loses. Exit 0
   = whole, 1 = torn, 3 = promote incomplete (try again), 2 = config.
   gxReplPromote() is the library call. "gxrepl torn" stays read-only
   and lists open stages as STAGED warnings. "gxrepl serve
   --accept-both" runs promote --apply before it starts serving.
   GXREPL_PROMOTE_LOCK_WAIT (default 480 s) bounds its wait for a
   running apply.

7. Dead copy folders. When the source removes a unit folder (for

   example a day folder archived at night), the copy used to delete
   only the files gxrepl copies; derived indexes, derived.stamp and
   other files gxrepl does not copy stayed behind, and promote-check
   refused the copy (UNSEALED) until the folder was removed by hand.
   Now a sealed unit whose last copied file goes is removed whole: its
   stage, the files gxrepl does not copy, the folder, its derived
   state and then its seal, under the apply lock after journal
   recovery. A server sweep (every GXREPL_SWEEP_SEC, 60 s) and the
   start-up recovery remove dead folders left by an older gxrepl or a
   stop part way (gxReplSweepDeadCopies()).
   It never removes an unsealed folder, a "copying" seal, a folder
   with a commit block, a copied file, a sub-folder, a configured
   writer lock, or any file that is not derived, default-excluded or
   derived.stamp; never while the set's writer holds its locks; and
   only on a node that is purely the set's copy (accept = target, or
   a pulling client). The sweeps leave a folder changed in the last
   GXREPL_DEAD_QUIET_SEC (600 s).

   gxStream servers now require client certificates and accept only
   the clients in an allow list. The check is on by default for
   database servers and off for other TLS servers.

   Servers
   - New gxStreamServer (gxstream.h), a gxsTLSServer for gxStream
     clients. Before Listen(), call SetClientCAFile("client_ca.pem")

     AllowClientCN(name). Listen() fails, with Error() saying why,

     Accept(gxStream &) accepts a client into a stream.
   - New gxsTLSServer functions: SetClientCAFile(), ClientCAFile(),

     certificate. Only the CAs in that file are trusted for client
     certificates, not the system store. After the handshake

     verifies, and that its SHA-256 fingerprint or subject CN is in

What changed

1. File I/O without stdio (gxdfptr.h, gxdfp64.h)

   Linux reads and writes with pread()/pwrite(), Windows (MSVC) with
   ReadFile()/WriteFile() and an OVERLAPPED offset, at a position kept
   in the stream, for both the 32-bit and 64-bit engines. A seek no
   longer costs a system call (it was about 20 system calls per
   database operation), and there is no stdio buffer to discard.
   New functions: gxdFPTRReadAt(), gxdFPTRWriteAt(), gxdFPTRSync(),
   gxdFPTRTruncate(), gxdFPTRAllocate(). gxdFPTRSeek(gxDBASE_SEEK_END)
   now seeks from the end of the file (it seeked from the current
   position). On Linux gxdFPTRFlush() has nothing to flush: writes go
   straight to the kernel. gxdFPTR64 keeps its FILE *fptr member (a
   stream on the same descriptor) so fileno(GetFP()->fptr) still works.

2. Real durability (gxdbase.h)

   gxDatabase::Sync(int full = 0) forces the file to disk (fdatasync,
   or fsync with full set; FlushFileBuffers on Windows).
   SetSyncOnFlush(1) makes Flush() sync as well. Before 7.2 Flush()
   stopped at the operating system's buffers.

3. Page cache (gxdpcache.h)

   gxDatabase::EnablePageCache(bytes) keeps 4 KB pages of the file in
   memory; every gxDatabase read and write uses it, so B-tree nodes,
   block headers and objects are read from memory once loaded. Outside
   a transaction it writes through, so the file is the same as without
   it. Use it only while one gxDatabase object owns the file.

4. Atomic, crash and power loss safe transactions (gxdjrnl.h)

   gxdJournal is a write-ahead log for a group of files (a data file
   and its index files):

     gxdJournal j;
     j.Open("orders.jnl");          // replays committed work
     db.Open("orders.gxd"); btx.Open("orders.btx");
     j.Attach(&db); j.Attach(&btx); // and a BtreeCache if used
     j.Begin(); ... j.Commit();      // Commit(1): synced, durable
     j.Close();                     // checkpoint, then close the files

   A commit appends the changed pages to the journal with one sync,
   then writes them to the files without a sync, so other processes
   reading the files see the batch when Commit() returns
   (write-through, the default). A checkpoint syncs the files and
   empties the journal when it passes 8 MB and on Close(), which also
   truncates it. After a program crash or power loss Open() writes
   every committed transaction to the files and drops one that did not
   commit, so a batch is all or nothing. Commit(0) skips the journal
   sync: safe from a program crash, but in write-through mode a power
   loss can leave part of that batch in the files. Rollback() drops the
   open transaction.

   SetWriteMode(gxdJOURNAL_WRITE_BACK) keeps committed pages in memory
   until a checkpoint (64 MB): fewer writes for a program that is the
   only user of the files, but other processes do not see the data
   until then. SetSyncLevel(OFF) skips the checkpoint syncs for
   Commit(0) work, like the "no sync" setting of embedded SQL databases.

   Readers in other processes see whole batches after Commit()
   returns. A reader that runs while a commit writes its pages can see
   part of the batch: use the application's own change counter, or
   SetWriteLock(1) in the writer and gxdJournalReadLock (a shared
   flock()/LockFileEx() lock on the journal file) in the readers.

5. B-tree cache (btcache.h)

   BtreeCache::FindBucket() used a linear walk of the buckets, so a big
   cache was slower than a small one (a 64 MB cache made random reads
   33 times slower). It is a hash lookup now. BtreeCache::Flush()
   writes the dirty buckets and keeps them, instead of emptying them.
   New: BtreeCache::Discard(). With the B-tree and its BtreeCache
   attached to a gxdJournal the cached B-tree is crash safe.

   NOTE: without the journal, a crash in the middle of a batch can
   still lose B-tree keys, as in 7.1 (cached nodes reach the file in
   cache order, and each node change is a separate write). Use
   gxdJournal for any index that must survive a crash or power loss.

6. B-tree reads (gxbtree.h)

   A node is read and written with one call each (it was three).
   Find(), FindFirst() and FindNext() reuse one node kept in the
   gxBtree, so a walk in key order reads the next key from the same
   leaf instead of searching from the root, while the file has not
   been written since (gxDatabase::WriteCount()).

7. Padding bytes

   gxFileHeader, gxBlockHeader and gxBtreeHeader zero their padding
   bytes, which were written to files with whatever the memory held.

  • Database and index files: unchanged. The nine database examples write byte-identical files with 7.1 and 7.2 in the 32-bit and 64-bit engines.
  • Source: the gxDatabase, gxBtree, BtreeCache, POD and InfoHog APIs are unchanged; everything new is added.
  • Binary: gxdFPTR64, gxDatabase, gxBtree and BtreeCache have new members. Rebuild programs against 7.2 (the vendored copies in OSA and OCA are rebuilt anyway).

Networking

  • gxSocket supports IPv4 and IPv6. Connect(host, port, timeout) tries every address a name resolves to; Listen(port) listens on one dual-stack socket; Accept() returns the client as a new gxSocket (the old remote_socket/RemoteRecv/RemoteSend server model is gone). Windows builds use Winsock 2.

Bug and security fixes

  • BtreeBucket::ReadNode() (the cached B-tree) trusted the key count in the index file; a damaged or crafted file overflowed the heap. This is the cached version of the gxBtree::ReadNode() fix in 6.1.
  • The cached B-tree walks stop after gxBtreeMaxNodeReads node reads, like the uncached walks in 6.2.
  • InfoHog::Read() and gxPersistent::ReadString() checked lengths read from the file through a signed cast, so very large lengths passed the check. gxDatabase::CalcChecksum() could allocate a huge buffer from a damaged block header. All now return an error.
  • gxrdDatabaseRecord::Compare() did not match a search string without a null against a stored string with its null, so gxRDBMS searches on CHAR fields found nothing.
  • gxDatabase::FindNextObject() and FindNextBlock() skipped a block when given an object address and returned the last block again at the end of the file, so a walk never ended.   • The B-tree cache did not work on index files opened read only.
  • gxTelnetClient's terminal type, long database file names and the serial block server could overflow buffers or allocate without limit.
  • Table header padding bytes are zeroed instead of left over memory.
  • The SMTP Date header is RFC 5322 (numeric time zone).

  • tests/run_tests.sh on RHEL 10: 42 checks covering every database example, InfoHog, gxRDBMS, TLS echo over IPv4 and IPv6, certificate rejection, HTTPS (including path traversal and http:// refusal), gxStream, SMTP (implicit TLS, STARTTLS, refusing a server without STARTTLS), POP3 (implicit TLS and STLS) and FTPS (explicit and implicit, upload, list, download) and the AI guide samples, in 32-bit and 64-bit engine, native and portable type, and static and shared library builds.
  • tests/damaged_files read thousands of randomly damaged database, index and InfoHog files without a crash or endless loop, and ran clean under valgrind.
  • The database examples, InfoHog and gxRDBMS programs were run with 6.2 and 7.0 and wrote identical files; 7.0 opened the 6.2 files.
  • Windows 11 with Visual Studio 2026, with both Schannel and OpenSSL 3.5: every example and test passed, including HTTPS to a public site through the Windows certificate store, the mail and FTPS clients against the Linux mock servers, and a Linux OpenSSL client with a Windows Schannel server.

Supported platforms

  • Linux: Red Hat Enterprise Linux 10 (the default build platform), 9 and 8, with the system OpenSSL.
  • Windows: Windows 11 and Windows Server 2022 and 2025, 64-bit, with Visual Studio 2022 or 2026, using Schannel or OpenSSL 3.5.x LTS.
